# セルフホストのトラブルシューティング

まずはサポートされた読み取り専用チェックから始めます。症状が消えるまでホスト設定を何度も書き換えるのではなく、最初に返された固定エラーコードを必ず控えておいてください。

## 初動チェック

```bash
./self-host status --json
./self-host doctor --json
./self-host logs --tail 200 --service server --service client --json
```

Docker が利用できない場合でも、`doctor` は実施可能な検査結果を報告します。リストアやアップグレードに失敗した場合は、レポートと未完了マーカーをそのまま保持してください。通常起動を強制するためにマーカーを削除しないでください。

## よくある問題と対処法

| 症状 | 確認する項目 | 安全な次のアクション |
| --- | --- | --- |
| インストーラーがリリースを拒否する | 外側チェックサム、Cosign のアイデンティティ、厳密バージョン、ダウンロードファイルの欠落 | 同じ公式リリースから一式をダウンロードし直す |
| サイトが開かない | `status`、Client ログ、バインドアドレス、ポート競合、HTTPS オリジン | 宣言済みの設定を修正し、`start --dry-run` の後に `start` を実行する |
| データベースに接続できない | `doctor` 内の DB サービス状態、ディスク容量、権限、マイグレーション結果 | ホスト容量や権限を復旧する。PostgreSQL を直接公開・編集しない |
| アップロードに失敗する | データルートの空き容量、inode 残量、所有権、uploads ディレクトリ | 専用データボリュームを拡張し、`doctor` を再実行する |
| AI 設定が表示されない | デプロイモード、インスタンス起動状態、サインイン中の Owner アカウント | 作成済みの Owner としてサインインする（Owner 以外はプロバイダー設定の閲覧・変更不可） |
| AI リクエストが失敗する | プロバイダー稼働状況、正確な Base URL、モデル ID、キーの権限、外部への DNS / TLS | Owner 管理の AI 設定を修正するか、プロバイダー障害中は AI を無効にする |
| リストア後に AI が失敗する | リストア先が異なるインスタンス認証シークレットを使用していないか | 新しいプロバイダーキーを入力する。古い平文キーを抽出しようとしない |
| リストアがブロックされる | ターゲットバージョン、ターゲット環境の状態、バックアップマニフェスト、チェックサム、レポート | クリーンな同一厳密バージョン環境を用意し、失敗した環境は診断用に残す |
| アップグレードがブロックされる | サポート対象の移行元バージョン、マイグレーション一覧、バックアップ、ディスク容量、ロールバック宣言 | アップグレードレポートに従う。イメージタグやマイグレーション記録を手動変更しない |

## 診断情報を収集する

`doctor` だけでは原因を特定できない場合、診断バンドルを取得します。

```bash
./self-host diagnostics --output support-<yyyy-mm-dd> --tail 500 --service server --service client --json
```

診断バンドルには自動マスクが適用されますが、自動マスクがあるからといってそのまま公開してよいわけではありません。必ずローカルで中身を開き、ホスト名、ユーザーデータ、アクティビティ詳細、業務ログが含まれていないか確認したうえで、メンテナーが指定する非公開チャネル経由で共有してください。

以下は決して共有しないでください。

- `.env.selfhost`
- Owner パスワードまたはブートストラップトークン
- プロバイダー API キー、Cookie、秘密鍵
- データベースダンプまたはアップロード済みアクティビティファイル
- 中身を確認していない診断バンドル

## 避けるべき操作

- `docker compose down -v` を実行しない。
- PostgreSQL データ、アップロードファイル、データルートマーカー、操作ロック、未完了ライフサイクルマーカーを削除しない。
- `_prisma_migrations`、リリースマニフェスト、チェックサム、アップグレードレポートを手動編集しない。
- `--skip-verify` や可変イメージタグを使用しない。
- 状態を変更するコマンドを並列に再実行しない。

これらの操作は、本来診断・復旧可能な障害を、回復不能または原因不明のデータ損失へ悪化させる恐れがあります。

## サポートへエスカレーションする際の情報

共有するのは、厳密なリリースバージョン、ホスト OS とアーキテクチャ、固定の `error.code`、失敗したコマンド、ローカルで確認済み診断バンドルの SHA-256 ハッシュのみにとどめてください。メンテナーから承認された転送チャネルの案内があるまで、診断バンドル本体は非公開のまま保管してください。

## 次のステップ

ブロック要因が解消したら、[インスタンスの運用管理](/ja/docs/self-host/operations)へ戻ってください。データの入れ替えによる復旧が必要な場合は、障害が起きたインスタンスへ上書きせず、クリーンな環境へ検証済みバックアップをリストアしてください。
