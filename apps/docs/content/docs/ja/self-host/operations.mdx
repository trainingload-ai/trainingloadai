# セルフホストインスタンスを運用管理する

インスタンスの操作には、Linux・macOS・WSL2 では `./self-host <command> --json`、Windows PowerShell では `.\self-host.ps1 <command> --json` を使用してください。この管理コマンドを使うことで、リリースが備える検証、ロック制御、監査記録、データ保護ルールが維持されます。

## 始める前に

- インストール済みのリリースディレクトリと `.env.selfhost` は非公開に保ってください。
- 自動化スクリプトの成否判定には人間向けメッセージではなく、JSON の `ok`、`exitCode`、`error.code`、`details` を使用してください。
- 状態を変更する操作の前には、必ず同じコマンドを `--dry-run` 付きで実行してください。
- `docker compose down -v` の実行、ライフサイクルマーカーの削除、データベースの手動ダウングレードは絶対に行わないでください。

## ステータス・ヘルス・ログを確認する

```bash
./self-host status --json
./self-host doctor --json
./self-host logs --tail 200 --service server --service client --json
```

`status` は範囲を絞った稼働状況のスナップショットを返します。`doctor` は信頼済み設定、ホストリソース、データパス、データベース状態、起動完了状態（Readiness）、有効なプロバイダーを検査します。ログは自動マスクと行数制限が適用されますが、業務データが含まれる場合があるため、共有前に必ず内容を確認してください。

## 起動と停止

```bash
./self-host start --dry-run --json
./self-host start --json

./self-host stop --dry-run --json
./self-host stop --json
```

停止してもコンテナ、設定、永続データは保持されます。データを残したままランタイムリソースを削除したい場合は、手順化された `uninstall` フローを使用してください。ボリュームを手動で削除しないでください。

## 検証済みバックアップを作成する

```bash
./self-host backup --output weekly-<yyyy-mm-dd> --dry-run --json
./self-host backup --output weekly-<yyyy-mm-dd> --json
```

バックアップには PostgreSQL の論理ダンプと正規のアップロードファイルが含まれます。キャッシュ、診断ファイル、ブートストラップトークン、TLS の秘密状態、ローカル昇格データ、シークレット値は含まれません。作成したバンドルはホスト外の暗号化ストレージに保管し、定期的にクリーンな隔離環境でリストア検証を行ってください。

## 安全にリストアする

リストアは、正規のデータベースとアップロード領域が空である、新規初期化済みの同一厳密バージョン環境に対してのみ実行してください。

```bash
./self-host restore /secure/path/to/backup --dry-run --json
./self-host restore /secure/path/to/backup --json
./self-host doctor --json
```

稼働中のインスタンスに上書きリストアしないでください。リストアに失敗した場合、不完全な環境が正常なインスタンスとして誤起動されないよう、ブロッキングマーカーとレポートが残されます。

## アップグレードする

アップグレードには、完全な署名済みターゲットリリースディレクトリが必要です。現在のインスタンス、ターゲットバンドル、検証済みのホスト外バックアップをそろえたうえで、現行コントローラーとターゲットコントローラーの両方で互換性ドライランを実行してから、ターゲット側の本実行へ進みます。

```bash
instance='/absolute/path/to/current-instance'
target='/absolute/path/to/trainingload-selfhost-<target-version>'

"$instance/self-host" upgrade "$target" --directory "$instance" --dry-run --json
"$target/self-host" upgrade "$target" --directory "$instance" --dry-run --json
"$target/self-host" upgrade "$target" --directory "$instance" --json
"$target/self-host" doctor --directory "$instance" --json
```

データベースマイグレーションは前方適用のみ（フォワードオンリー）です。アプリケーションのロールバックが利用可能なのは、アップグレードレポートに明示的にロールバック可能と記載され、かつ旧イメージが検証可能な状態に残っている場合に限られます。ロールバックでデータベースがダウングレードされることはありません。

## 推奨される運用ルーチン

- **毎日：** `status` とディスク空き容量を確認する。
- **毎週：** `doctor` を実行し、検証済みのホスト外バックアップを作成する。
- **アップグレード前：** ターゲット版のリリースノートを確認し、バンドルを検証し、バックアップをテストしてロールバック可否の記載を確認する。
- **定期的：** 隔離環境へバックアップをリストアし、Owner・アクティビティ・アップロードファイルが正常に復元されるか訓練を行う。

## 確認項目

- 状態を変更するすべての操作の前に、同一コマンド・同一引数で `--dry-run` を実行した。
- 起動・リストア・アップグレード後に `doctor` が `"ok": true` を返す。
- ホスト外に最新の検証済みバックアップが少なくとも1つ保管されている。
- バックアップが存在するだけでなく、リストア訓練で実際に復元可能であることを確認済みである。

## トラブルシューティング

操作に失敗した場合は、固定のエラーコードを控えたうえで `doctor` を実行してください。診断バンドルは必要なときにのみ作成し、ローカルで中身を確認してください。生の `.env.selfhost`、データベースダンプ、アップロードファイル、パスワード、トークン、プロバイダーキーは絶対に公開しないでください。別の操作がインスタンスロックを保持している間は、状態変更コマンドを並列再実行しないでください。
