# 셀프 호스팅 문제 해결

먼저 공식 읽기 전용 점검 명령부터 실행합니다. 증상이 사라질 때까지 호스트 설정을 무작정 바꾸는 것보다 가장 먼저 반환된 안정적 오류 코드를 보존하는 것이 훨씬 중요합니다.

## 초기 대응

```bash
./self-host status --json
./self-host doctor --json
./self-host logs --tail 200 --service server --service client --json
```

Docker를 사용할 수 없는 상황에서도 `doctor`는 수행 가능한 점검 결과를 보고합니다. 복원이나 업그레이드에 실패했다면 생성된 리포트와 미완료 마커를 그대로 보존하세요. 강제로 정상 시작하려고 마커를 삭제해서는 안 됩니다.

## 자주 발생하는 문제

| 증상 | 확인할 항목 | 안전한 다음 조치 |
| --- | --- | --- |
| 설치 프로그램이 릴리스를 거부함 | 외부 체크섬, Cosign 인증 ID, 정확한 버전, 모든 릴리스 파일 다운로드 완료 여부 | 동일한 공식 릴리스에서 모든 아티팩트를 다시 다운로드합니다 |
| 사이트가 열리지 않음 | `status`, Client 로그, 바인드 주소, 포트 충돌, HTTPS 오리진 설정 | 선언된 설정을 수정한 뒤 `start --dry-run`을 거쳐 `start`를 실행합니다 |
| 데이터베이스를 사용할 수 없음 | `doctor`의 데이터베이스 서비스 상태, 디스크 용량, 권한, 마이그레이션 결과 | 호스트 용량이나 권한을 복구합니다. PostgreSQL을 외부에 노출하거나 직접 수정하지 마세요 |
| 파일 업로드 실패 | 데이터 루트 여유 공간, inode 용량, 소유권, 업로드 디렉터리 상태 | 전용 데이터 볼륨을 확장한 뒤 `doctor`를 다시 실행합니다 |
| AI 설정 메뉴가 보이지 않음 | 배포 모드, 인스턴스 준비 상태, 로그인된 Owner 계정 일치 여부 | 생성된 Owner 계정으로 로그인합니다. 비-Owner는 공급자 설정을 보거나 바꿀 수 없습니다 |
| AI 요청 실패 | 공급자 서비스 상태, 정확한 Base URL, 모델 ID, 키 접근 권한, 아웃바운드 DNS/TLS | Owner 관리 설정을 수정하거나 공급자 장애 중에는 AI를 비활성화합니다 |
| 복원 후 AI가 실패함 | 대상 인스턴스가 다른 인증 시크릿을 사용하고 있는지 여부 | 새 공급자 키를 다시 입력합니다. 기존 평문 키를 추출하려고 시도하지 마세요 |
| 복원이 차단됨 | 대상 버전, 대상 상태, 백업 매니페스트, 체크섬, 오류 리포트 | 깨끗한 동일 버전 대상을 사용하고, 실패한 대상은 진단용으로 보존합니다 |
| 업그레이드가 차단됨 | 지원되는 소스 버전, 마이그레이션 목록, 백업, 디스크 공간, 롤백 선언 | 업그레이드 리포트 지침을 따릅니다. 이미지 태그나 마이그레이션 기록을 수동 편집하지 마세요 |

## 진단 자료 수집하기

`doctor`만으로 원인이 충분히 파악되지 않을 때는 다음 명령을 실행합니다.

```bash
./self-host diagnostics --output support-<yyyy-mm-dd> --tail 500 --service server --service client --json
```

진단 번들에는 자동 마스킹이 적용되지만, 자동 마스킹이 곧 공개 배포 허용을 의미하지는 않습니다. 유지 관리자가 승인한 비공개 채널로 전달하기 전에 반드시 로컬에서 파일을 열어 호스트명, 사용자 데이터, 활동 세부 정보, 업무 로그가 남아 있지 않은지 확인하세요.

절대 공유하지 말아야 할 항목:

- `.env.selfhost`
- Owner 비밀번호 또는 부트스트랩 토큰
- 공급자 API 키, 쿠키, 개인 키
- 데이터베이스 덤프 또는 업로드된 활동 파일
- 직접 검토하지 않은 진단 번들

## 피해야 할 행동

- `docker compose down -v`를 실행하지 마세요.
- PostgreSQL 데이터, 업로드 파일, 데이터 루트 마커, 작업 잠금, 미완료 수명 주기 마커를 삭제하지 마세요.
- `_prisma_migrations`, 릴리스 매니페스트, 체크섬, 업그레이드 리포트를 수동으로 편집하지 마세요.
- `--skip-verify`나 가변(mutable) 이미지 태그를 사용하지 마세요.
- 상태 변경 명령을 병렬로 재시도하지 마세요.

이러한 행동은 진단 가능한 장애를 복구 불가능하거나 원인을 알 수 없는 데이터 손실로 악화시킬 수 있습니다.

## 유용한 근거로 지원 요청하기

정확한 릴리스 버전, 호스트 OS 및 아키텍처, 안정적 `error.code`, 실패한 명령어, 그리고 로컬에서 검토를 마친 진단 아티팩트의 SHA-256 해시만 먼저 공유하세요. 전체 진단 번들은 유지 관리자가 승인한 전달 채널을 안내하기 전까지 비공개로 유지해야 합니다.
