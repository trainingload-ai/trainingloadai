# 持续训练计划

`Plan.planningMode` 明确区分 `FIXED` 与 `ROLLING`。固定计划继续使用相对起点的计划周与有限 `periodWeeks`；持续计划的 `periodWeeks` 和 `endDate` 为空，不会在已生成周结束时完成。课程位置仍相对原始起点，实际训练预算与生成按 ISO 自然周统计。

持续草稿通过既有完整 START 对话准备。一次真实卡片确认在同一串行化事务中启用同一个 Plan、保存用户自动管理策略、当月方向与首个自然周剩余日期的课程。跨月周引用两个自然月策略；月中开始的策略只从开始日生效。月目标是可修订的预测，不是以后必须补做的欠账。

自动管理策略、自然月策略及自然周生成记录都有修订。数据库条件唯一索引保证同一个 Plan 只有一个有效授权、同一自然月或自然周只有一个已生效版本。课程通过 `generationId` 关联实际发布记录。人工安排过的未来课程可标记为自动化保护项。

`generatedThrough` 仅表示最远已发布日期。日期是否已生成以 `generationCoverage.intervals` 为准；暂停或失败后的缺口不会被最大日期覆盖。窗口状态为 `NOT_GENERATED`、`PARTIAL` 或 `GENERATED`。没有覆盖且没有课程的日期是 `NOT_GENERATED`，不能解释为休息日。公开详情与教练查询对持续计划返回明确的有限日期窗口；历史查询通过有界日历接口读取。

`PlanStartService.createAutomationPreview(jobId, claimToken, request)` 与 `applyAutomation(jobId, claimToken)` 是服务端端口，不注册为 HTTP 或模型工具。端口从数据库任务取得归属、策略与窗口，核验当前有效授权、计划状态、租约、任务类型、月策略依赖、计划建议权益和同事务 AI 数据同意，再复用提案的候选校验、原子写入和读回。自动应用写入自己的 Commit 与 `AUTOMATION_POLICY` 回执，不创建或伪造用户确认 Decision。周/月调度、模型编排、任务领取和恢复由上层运行时负责，计划模块不反向依赖 AI 或 Review 模块。

整个持续计划不能编码为有限可复用的 `plan-share-v1` 模板。`window-snapshot` 返回最长 93 日、明确标记 `plan-window-v2` 和 `snapshotOnly` 的日期工件，保留生成区间和未知负荷；它不携带自动管理授权，也不能冒充完整自动计划导入。账户数据导出升级为 `trainingload-export/v2`，保留模式、空周数、策略修订和实际生成区间。固定 v1 计划分享合同保持不变。

窗口负荷分别呈现实际活动、剩余课程预计和未生成预测。实际值来自统一活动负荷读取；关联活动与额外训练按活动身份去重，已完成课程不再叠加预计负荷。未知值保留 `null` 与覆盖数量、来源和统一单位，不将缺记录解释成零。游泳 TP 与 CS 都以 m/s 保存，预计负荷统一换算为 sec/100m 后使用既有公式。
